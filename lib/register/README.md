# کنترل رویژن رجیستر (EPIC-2)

> سند مرجع: `docs/epc-llm/03-implementation-backlog.md` EPIC-2 ·
> سند ۰۰ بند ۸ این را «پرارزش‌ترین قابلیت فاز ۱» می‌نامد

## تغییر طراحی نسبت به بک‌لاگ

بک‌لاگ برای story 2.1 گفته بود: «`weld_uid` پایدار از `(line_no, joint_kind,
موقعیت روی مسیر)` تولید شود.»

**این کار نمی‌کند** — و دلیلش یک جزئیات پیاده‌سازی نیست، بلکه ماهیت مسئله است.
هر هویتِ **مشتق‌شده** در یکی از دو اتفاقی که واقعاً بین رویژن‌ها می‌افتد شکست
می‌خورد:

| مبنای هویت | چه چیزی می‌شکندش |
|---|---|
| شمارهٔ جوش | یک اتصال که بالادست اضافه شود، همهٔ جوش‌های پایین‌دست را شماره‌گذاری مجدد می‌کند — جوش‌هایی که اصلاً تکان نخورده‌اند «جدید» به نظر می‌رسند |
| موقعیت فضایی | یک ابعاد جاری که اصلاح شود، کل مسیر را جابه‌جا می‌کند — باز هم همه‌چیز جدید به نظر می‌رسد |

هیچ فرمولی از هر دو جان سالم به در نمی‌برد، چون **«آیا این همان جوش است؟»
خاصیت یک جوش نیست؛ رابطه‌ای بین دو رجیستر است.**

پس هویت اینجا یک **surrogate** است: یک بار ضرب می‌شود، بعد با **تطبیق** به جلو
منتقل می‌شود. و همان محاسبهٔ تطبیق، diff رویژن را هم تولید می‌کند. یک مکانیزم،
دو خروجی.

## چرا tie-in لنگر است

روی یک ایزومتریک، tie-in تنها چیز **قراردادی** است: مختصاتش چاپ شده و شمارهٔ
نقشهٔ ادامه‌اش ارجاع به یک برگ مشخص دیگر است.

پس:

۱. tie-in ای که `role` (همان شمارهٔ نقشهٔ ادامه) یکسان دارد، تقریباً قطعی است
۲. **اختلاف موقعیت بین یک جفت tie-in منطبق، برای تراز کردن دو رجیستر استفاده
   می‌شود، قبل از اینکه هیچ فاصله‌ای اندازه گرفته شود**

مورد دوم همان چیزی است که باعث می‌شود رویژنی که فقط مبنای مختصات (datum) را
عوض کرده، **یک no-op** باشد نه بازنویسی کامل. بدون آن، هر ده جوش «حذف و دوباره
اضافه» گزارش می‌شدند.

## جدول وزن‌ها

در `match.mjs` و عمداً در یک جا، تا تنظیمش یک تصمیم دیده‌شده باشد:

| سیگنال | وزن | چرا |
|---|---|---|
| `anchorRole` | ۱۰۰ | شمارهٔ نقشهٔ ادامهٔ tie-in — قوی‌ترین سیگنال موجود |
| `distExact` (≤۲mm) | ۶۰ | بعد از تراز، همان نقطه |
| `distClose` (≤۵۰mm) | ۴۰ | گرد کردن یا تغییر pup |
| `distNear` (≤۵۰۰mm) | ۲۵ | اصلاح ابعاد محلی |
| `distFar` (≤۲m) | ۱۰ | احتمالاً همان همسایگی |
| `kind` | ۲۰ | |
| `nps` | ۱۵ | |
| `role` | ۱۰ | |
| `ordinal` | ۸ | همان اندیس از یکی از دو سر رجیستر |

**کف ۴۵ امتیاز:** زیر این، دو ردیف یک جوش نیستند، هرچند سیگنال ضعیف که با هم
بخوانند.

تطبیق **حریصانه** است نه بهینه — و این انتخاب است: یک رجیستر ده‌ها ردیف دارد،
امتیازها وقتی تطبیق واقعی باشد فاصلهٔ زیادی دارند، و مهندسی که diff را
می‌خواند می‌تواند «بهترین جفت باقی‌مانده، بعد بعدی» را دنبال کند — چیزی که در
یک تخصیص سراسری بهینه نمی‌تواند.

## آنچه diff می‌دهد

```
added        جوش‌هایی که در رویژن جدید ظاهر شده‌اند
removed      جوش‌هایی که رفته‌اند
changed      جفت‌های منطبق با اختلاف: محل، نوع، قطر، اسپول، اتصال، NDT، موقعیت
unchanged    منطبق و یکسان
renumbered   شماره عوض شده ولی کار عوض نشده — جدا گزارش می‌شود
rebased      مبنای مختصات جابه‌جا شده و با tie-in تراز شد
```

«شماره‌گذاری مجدد» جدا گزارش می‌شود چون **تغییری در کار نیست**، ولی دقیقاً همان
چیزی است که یک رجیستر را غیرقابل‌تشخیص نشان می‌دهد.

## اثر روی اسپول — بخشی که پول خرج می‌کند

```js
spoolImpact(diff, fabStatusBySpool)
  → { spools, rework, safe }
```

اسپولی که هنوز روی کاغذ است، یک رویژن را **رایگان** جذب می‌کند. اسپولی که
جوشکاری، تست و رنگ شده، همان رویژن را به‌صورت **برش و جوش مجدد، گزارش NDT
جدید، و تأخیر** جذب می‌کند.

پس پاسخ بر اساس وضعیت ساخت تفکیک می‌شود، نه به‌صورت یک فهرست. `rework` همان
زنگ خطر است: کاری که انجام شده و این رویژن باطلش می‌کند.

**جوشی که بین دو اسپول جابه‌جا شود، به هر دو آسیب می‌زند** — اسپولی که ترکش
کرده یک جوش کم دارد و اسپولی که واردش شده یک جوش اضافه.

## وضعیت ساخت اسپول

`migration 002` ستون `fab_status` را اضافه می‌کند:
`planned → released → fabricated → tested → painted → shipped → erected`

وضعیت روی ردیف اسپولِ یک **اجرای مشخص** می‌نشیند، پس همیشه معلوم است رجیسترِ
کدام نسخه ساخته شده. تطبیق یک اسپول ساخته‌شده با نظیرش در رویژن بعدی،
**از روی جوش‌های مشترکشان مشتق می‌شود، نه ذخیره** — شمارهٔ اسپول دقیقاً مثل
شمارهٔ جوش، شماره‌گذاری مجدد می‌شود.

ثبت وضعیت یک **شهادت** است، پس `fab_status_by` و `fab_status_at` هم ثبت می‌شوند.

## API

```
GET  /api/runs/[id]/diff?projectId=…              در برابر اجرای قبلی همان برگ
GET  /api/runs/[id]/diff?projectId=…&against=…    در برابر یک اجرای مشخص
POST /api/spools/[id]/status                      ثبت پیشرفت ساخت (نقش qc)
```

مقایسهٔ دو نقشهٔ متفاوت با `DIFFERENT_DRAWINGS` رد می‌شود. نقشه‌ای که اجرای
قبلی ندارد `NO_PREVIOUS_RUN` می‌گیرد، نه یک مقایسهٔ ساختگی.

## تست

`db/test/revisions.mjs` — ۱۴ تست، در برابر سه چیزی که واقعاً اتفاق می‌افتد:

- **اصلاح ابعاد** → فقط جوش‌هایی که جابه‌جا شدند `changed` می‌شوند، بالادستشان نه
- **تغییر datum** → صفر تغییر، و `rebased` گزارش می‌شود
- **اتصال جدید وسط مسیر** → جوش‌های جدید `added`، هیچ‌چیز `removed` نمی‌شود،
  هر دو tie-in از شماره‌گذاری مجدد جان سالم در می‌برند

به‌علاوه مسیر کامل از API: ضرب هویت در اجرای اول، انتقالش در رویژن بعدی از مرز
سند، و تبدیل شدن diff به هشدار دوباره‌کاری وقتی اسپول `fabricated` باشد.
