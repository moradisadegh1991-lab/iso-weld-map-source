# ایزومتریک‌های واقعی در برابر رجیستر پیمانکار — یک واحد پروژهٔ HDPE

> داده‌ها (نقشه‌ها، MTO، رجیستر پیمانکار) متعلق به پروژه‌اند و **در این مخزن نیستند**؛
> این سند فقط روش، عددها و آنچه از آنها یاد گرفته شد را نگه می‌دارد.

## داده

| | |
|---|---|
| نقشه | ۵۵ برگ ایزومتریک PDF اسکن‌شده (rev 0 و یک 0A)، واحد ۲۵ |
| MTO | پایگاه Access پروژه، جدول `MTO-PPG` (۷۷ هزار ردیف، کل پروژه): BOM هر برگ |
| رجیستر | joint history پیمانکار (۱۱۳ هزار ردیف، کل پروژه) — **۸۰۹ جوش روی همین ۵۵ برگ** |

نوع جوش در آن ۸۰۹: SW ۴۵۲ · BW ۲۹۸ · THD ۳۲ · OLET ۲۵ · BR ۲. محل: سایت ۶۷۲، کارگاه ۱۸۶.
همهٔ SW، THD و OLET سایتی‌اند؛ کارگاه فقط BW.

## آنچه نقشه‌ها نشان دادند

هر جوش روی نقشه شماره دارد و شماره در قابی است که شکلش محل را می‌گوید: **دایره =
کارگاه، مربع = سایت**؛ «FFW» کنار جوش اتصال سایت، «THD» کنار بعضی اتصال‌های رزوه‌ای؛
جوشی که به برگ مجاور تعلق دارد با قاب **خط‌چین** کشیده شده. شماره‌های رجیستر پیمانکار
عیناً همین‌هاست. پس روی این نقشه‌ها رجیستر را طراح ساخته؛ کار استخراج **خواندن** آن است،
نه ساختن دوباره از هندسه — که تازه فقط BW را می‌شناسد (F-18).

## روش اندازه‌گیری

```bash
npm run weldmap:truth -- <پوشهٔ JSON استخراج> <joints_history.xlsx> --shop circle --field square [--thd-labelled]
```

هر JSON یک برگ است (`meta`، `bom`، `weldMarks`) — همان چیزی که صفحهٔ پایپینگ بعد از
استخراج نگه می‌دارد. رجیستر کل پروژه برای هر برگ به ردیف‌های خودش بریده می‌شود
(`scopeRows`). تعداد و شماره (جاافتاده و اضافه جدا)، محل، نوع و قطر سنجیده می‌شوند؛
فیلدی که قاعده خالی گذاشت **نه درست حساب می‌شود نه غلط**، جدا شمرده می‌شود.

## نتیجه — ۷ برگ، خوانده‌شده پیش از دیدن رجیستر

خواننده: Claude در جلسهٔ توسعه، به‌جای پاس `welds` (کلید API روی این محیط نبود). BOM از MTO.

| برگ | رجیستر | خوانده | اختلاف |
|---|---|---|---|
| ISO-25-1001 1/1 (0A) | 10 | 10 | — (جوش 4-1 افزوده در 0A هم خوانده شد) |
| ISO-25-1004 2/2 | 16 | 16 | 022 نوع: پیمانکار SW، قاعده BW (انشعاب سه‌راهی BW) |
| ISO-25-1005 1/1 | 22 | 22 | — |
| ISO-25-1007 1/1 | 3 | 3 | — |
| ISO-25-1017 1/4 | 28 | 28 | 018 قطر: 1½ نه ¾ (خطای خواندن) |
| ISO-25-1031 1/1 | 20 | 20 | 001 نوع: SW نه OLET (خطای خواندن)؛ 016: نقشه «THD» چاپ کرده، پیمانکار SW نوشته |
| ISO-25-1036 1/1 | 25 | 25 | — |

**جمع:** ۱۲۴ جوش — تعداد روی هر ۷ برگ دقیق، ۰ جاافتاده، ۰ اضافه · **محل ۱۰۰٪** (۱۲۴/۱۲۴) ·
**قطر ۹۹٫۲٪** · **نوع ۹۶٫۱٪** روی ۷۶ جوشی که قاعده حکم داد، ۴۸ خالی برای شخص.
با `--thd-labelled`: نوع ۹۷٫۶٪ روی هر ۱۲۴، بی‌خالی — ولی روی ۲۵-۱۰۰۲ یک درپوش رزوه‌ای
بدون برچسب THD هست؛ این گزینه را پروژه فقط پس از بررسی نقشه‌هایش اعلام کند.

مسیر هندسی قبلی روی همین ۱۲۴ جوش: ۹۲ SW و ۴ THD را اصلاً نمی‌توانست بسازد (سقف ۲۸ جوش، ۲۳٪)،
و شماره‌هایش (W-01…) با شماره‌های چاپ‌شده یکی نبود.

سه برگ دیگر (۲۵-۱۰۰۲، ۲۵-۱۰۱۲، ۲۵-۱۰۲۲ برگ ۲؛ ۷۸ جوش) پیش از نوشتن این ابزار خوانده
شدند و شماره و محل همه با رجیستر یکی بود؛ چون قطر و نوعشان پس از دیدن رجیستر نوشته
می‌شد، در عدد بالا نیستند.

## در مرورگر

`tools/drive-weldmap.mjs` همین مسیر را از فرم‌ها می‌راند: اعلام نماد جوش در «پروژه»،
بارگذاری PDF در «ایزومتریک و رجیستر جوش» (سه پاس؛ مدل با یک stub سازگار با OpenAI
پاسخ داد)، فهرست جوش ساخته‌شده از شماره‌های چاپ‌شده، و بارگذاری Excel کل پروژهٔ پیمانکار
در «حقیقت مرجع». روی ۲۵-۱۰۳۶ (۲۵ جوش) و ۲۵-۱۰۰۴ برگ ۲ (۱۶ جوش، با کارگاه و اسپول):
تعداد برابر، محل ۱۰۰٪، problems: none.

## قدم بعد

۱. کلید API (یا vLLM) روی سرور؛ هر ۵۵ برگ از صفحهٔ پایپینگ استخراج و JSON هر برگ ذخیره
   شود؛ `npm run weldmap:truth` روی آنها — عدد **پاس واقعی**.
۲. اختلاف‌هایی که نقشه و رجیستر با هم ندارند (مثل ۲۵-۱۰۳۱ جوش ۱۶) به مهندس پایپینگ:
   رجیستر پیمانکار هم خطا دارد، و عدد دقت فقط تا جایی معتبر است که مرجع درست باشد.
۳. نوع اتصال در سایز مخلوط (SW و رزوه‌ای ¾"): پاسی که دو جزء دو طرف هر جوش را با شمارهٔ
   BOM بخواند تا قاعده بدون حدس حکم دهد.
