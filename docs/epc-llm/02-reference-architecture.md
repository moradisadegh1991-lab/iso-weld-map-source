## ۲. انتخاب ابزار — با دلیل

### ۲٫۱ سرو مدل (L4)

| مؤلفه | انتخاب | چرا |
|---|---|---|
| موتور سرو | **vLLM** | استاندارد ۲۰۲۶. Hugging Face در آذر ۱۴۰۴ توسعهٔ TGI را متوقف و به vLLM/SGLang منتقل کرد. throughput بالا در batch |
| موتور سرو جایگزین | **SGLang** | برای بارهای RAG با prefix مشترک و مکالمهٔ چندنوبتی بهتر است. اگر RAG سنگین شد، همین را برای آن مسیر جدا کنید |
| API | سازگار با OpenAI | vLLM این را می‌دهد؛ یعنی کل کد ما مستقل از vendor می‌ماند و فردا قابل تعویض است |
| LLM متنی | **Qwen3-32B** (AWQ/GPTQ 4-bit) | چندزبانگی قوی (۱۰۰+ زبان، شامل فارسی)، مجوز تجاری، اندازهٔ مناسب یک GPU |
| LLM متنی — گزینهٔ بزرگ‌تر | **Qwen3-72B** یا **DeepSeek** | برای پاس «اصلاح» و استدلال؛ همان الگوی فعلی مخزن: استخراج سریع، اصلاح دقیق |
| VLM (نقشه و عکس) | **Qwen2.5-VL 32B/72B** یا **InternVL** | خواندن نقشهٔ اسکن‌شده، checksheet دست‌نویس، عکس میدانی |
| Embedding | **BGE-M3** | چندزبانه (فارسی + انگلیسی در یک فضا)، پشتیبانی dense + sparse + multi-vector |
| Reranker | **BGE-reranker-v2-m3** | بدون reranker، دقت RAG روی اسناد فنی به‌شدت افت می‌کند |
| OCR | **Surya** یا **PaddleOCR** + fallback به VLM | Tesseract برای فارسی چاپی متوسط و برای دست‌نویس ضعیف است |

> **نکتهٔ انتقالی:** تا زمانی که خوشهٔ داخلی بالا بیاید، مخزن فعلی روی API
> Anthropic کار می‌کند (`app/api/extract/route.js`). این را **به‌عنوان یک
> adapter نگه دارید، نه وابستگی**: یک interface واحد `llmClient` بسازید که
> هم `anthropic` و هم `vllm-openai` را پیاده کند. مهاجرت آنگاه یک تغییر
> پیکربندی است، نه بازنویسی.

### ۲٫۲ داده (L3)

| مؤلفه | انتخاب | چرا |
|---|---|---|
| پایگاه دادهٔ اصلی | **PostgreSQL 16+** | مدل دامنه: weld، spool، ITR، material، IWP. تراکنشی، قابل ممیزی |
| برداری | **Qdrant** (یا `pgvector` برای شروع) | فیلتر metadata قوی — برای «فقط در Spec پروژهٔ X و رویژن جاری» حیاتی است |
| شروع ساده | `pgvector` | تا زیر ~۵ میلیون chunk، جدا کردن یک سرویس دیگر ارزشش را ندارد |
| سری زمانی | **TimescaleDB** | نفر-ساعت، منحنی پیشرفت، داده حسگر در فازهای بعد |
| گراف | **Neo4j** یا جدول رابطه‌ای در PG | روابط system/subsystem، تگ‌ها، وابستگی punch. در فاز ۱ نیازی نیست |
| شیء خام | **MinIO** | نقشهٔ اصلی، PDF، عکس. سازگار با S3، کاملاً on-prem |
| کش | **Redis** | صف کار، کش نتیجهٔ استخراج (یک نقشه دوبار پردازش نشود) |

### ۲٫۳ هماهنگ‌سازی و عملیات (L6)

| مؤلفه | انتخاب | چرا |
|---|---|---|
| Workflow پایدار | **Temporal** | جریان استخراج ← اعتبارسنجی ← تأیید انسانی ← انتشار، ممکن است **روزها** طول بکشد. زنجیرهٔ prompt بدون حالت اینجا شکست می‌خورد |
| ایجنت | **LangGraph** | state machine صریح؛ از زنجیرهٔ خطی قابل‌کنترل‌تر است |
| اتوماسیون سبک | **n8n** | برای اتصال ایمیل، واچر پوشه، اعلان — بدون کد |
| Observability LLM | **Langfuse** (self-host) | trace هر فراخوانی، هزینه، تأخیر، و مهم‌تر: **کدام سند بازیابی شد** |
| Eval | **Ragas** + harness اختصاصی | معیارها: faithfulness، context precision/recall، groundedness. همان‌طور که تحقیق بازار نشان داد، **بیشترین برد production از زیرساخت ارزیابی می‌آید نه ارتقای مدل** |
| احراز هویت | **Keycloak** | SSO، RBAC، یکپارچگی با AD سازمان |
| CI/CD | **GitLab CI** یا Gitea Actions (داخلی) | eval باید در pipeline اجرا شود |
| پایش | **Prometheus + Grafana** | GPU utilization، صف، تأخیر |

## ۳. سایزینگ سخت‌افزار

### ۳٫۱ فاز ۱ — پایلوت (کمینهٔ کارا)

| مؤلفه | مشخصات | توضیح |
|---|---|---|
| GPU | **۲ × NVIDIA RTX 6000 Ada (48GB)** یا **۲ × L40S (48GB)** | یکی LLM متنی، یکی VLM. کوانتیزهٔ ۴-بیتی مدل ۳۲B روی ۴۸GB جا می‌شود |
| گزینهٔ اقتصادی | **۲ × RTX 4090 (24GB)** | فقط برای مدل‌های ≤۱۴B یا ۳۲B با کوانتیزهٔ تهاجمی؛ برای VLM روی نقشهٔ بزرگ تنگ است |
| گزینهٔ سقف | **۱ × H100 80GB** | اگر مدل ۷۲B بدون افت کیفیت لازم شد |
| CPU | ۳۲ هسته | پیش‌پردازش تصویر و کاشی‌بندی CPU-bound است |
| RAM | ۲۵۶ GB | |
| ذخیره‌سازی | ۴ TB NVMe (داغ) + ۲۰ TB HDD (آرشیو نقشه) | نقشه‌های ۳۰۰ DPI حجیم‌اند |
| شبکه | ۱۰ GbE داخلی | |

### ۳٫۲ محاسبهٔ ظرفیت واقع‌بینانه

فرض‌های پایلوت:
- ۵۰۰ ایزومتریک، هر کدام ۳ پاس (meta + nodes + repair)
- هر پاس با کاشی‌بندی ۳×۳ ≈ ۱۰ تصویر ورودی
- ورودی مؤثر ≈ ۲۰–۳۰ هزار توکن، خروجی ≈ ۴ هزار توکن

با یک GPU کلاس ۴۸GB و مدل ۳۲B کوانتیزه، **~۲–۴ نقشه در دقیقه** با batching
واقع‌بینانه است ⇒ کل ۵۰۰ نقشه در حدود ۳–۴ ساعت. برای پایلوت کاملاً کافی است.
گلوگاه واقعی **بازبینی انسانی** خواهد بود، نه GPU.

### ۳٫۳ رشد فاز ۲–۳

افزودن ۱–۲ GPU دیگر برای: سرو embedding جدا، مدل fine-tune شدهٔ گزارش روزانه،
و ظرفیت هم‌زمانی کاربران موبایل.

یک نگاشت باشد نه بازنویسی.

  weld_no, weld_type,      -- BW / SW / FW
  shop_field,              -- Shop | Field
  nps, schedule, material_spec,
  spool_id, joint_kind,    -- elbow | tee | flange | valve | girth | tie_in
  status, created_rev, superseded_rev
)

-- اسپول
spool(id, spool_no, line_id, length_mm, weight_kg, fab_status, shipped_at)

-- ردیابی اجرا (C-05, C-06)
weld_execution(
  weld_id, welder_id, wps_no, welded_at,

welder(id, stamp_no, name, qualified_processes, qualified_range, wqt_expiry)

-- NDT (C-03)
ndt(

  report_no, result, repair_cycle, inspected_at
)

-- متریال (C-07)
material_item(id, item_code, description, nps, schedule, spec, rating, uom)
material_txn(
  item_id, txn_type,       -- MTO | PO | MRR | MIR | INSTALLED | SURPLUS

## ۶. الگوی RAG برای اسناد فنی

RAG روی Spec و Piping Class با RAG روی متن عمومی **متفاوت** است:

| چالش | راهکار |
|---|---|
| جدول‌های فنی در PDF | استخراج جدول جدا از متن؛ هر سطر جدول یک chunk مستقل با سرستون تکرارشده |
| ارجاع بندی (§341.4.1) | حفظ سلسله‌مراتب بند در metadata؛ بازیابی بند والد همراه فرزند |
| رویژن اسناد | فیلتر اجباری `revision = current` در زمان بازیابی — بازیابی از Spec منسوخ یک باگ ایمنی است |
| دوزبانگی | BGE-M3 فارسی و انگلیسی را در یک فضا می‌نشاند؛ سؤال فارسی می‌تواند بند انگلیسی را بیاورد |
| دقت عددی | **هرگز** عدد را از خروجی مدل نپذیرید؛ عدد را از جدول ساخت‌یافته در Postgres بخوانید و مدل فقط بگوید «کدام سطر» |

**الگوی پیشنهادی (agentic RAG):**
```
سؤال → بازنویسی و تجزیه به زیرسؤال
     → انتخاب منبع (SQL ساخت‌یافته | برداری | گراف)
     → بازیابی ترکیبی (dense + BM25) → reranking
     → تولید با ارجاع اجباری
     → گاردریل: اگر ارجاع نداشت یا groundedness پایین بود → «نمی‌دانم» + ارجاع به انسان
```

## ۷. چارچوب ارزیابی (بدون این، هیچ ادعایی قابل اثبات نیست)

### ۷٫۱ دیتاست طلایی

| مجموعه | حجم هدف | ساخته‌شده توسط |
|---|---|---|
| ایزومتریک + رجیستر جوش دستی | ۵۰ | مهندس پایپینگ |
| RFI/TQ تاریخی با پاسخ نهایی | ۲۰۰ | مهندسی سایت |
| MRR/پکینگ‌لیست با داده تأییدشده | ۳۰۰ سطر | انبار |
| NCR با علت ریشه‌ای تأییدشده | ۱۰۰ | QC |
| گزارش روزانهٔ فارسی با برچسب‌گذاری دستی | ۲۰۰ | کنترل پروژه |

### ۷٫۲ متریک‌ها

**لایهٔ استخراج (L2–L4):**
- دقت فیلدی به تفکیک فیلد (`line_no`, `nps`, `revision`, `qty`)
- **exact match تعداد جوش** — سخت‌گیرانه‌ترین و معنادارترین متریک MVP
- نرخ ویرایش انسانی

**لایهٔ RAG (L4):**
- faithfulness · context precision · context recall · groundedness · نرخ توهم

**لایهٔ کسب‌وکار (L7):**
- زمان چرخه · نرخ دوباره‌کاری · مغایرت انبار · روزهای تأخیر تحویل مدارک

### ۷٫۳ قاعدهٔ CI

> هیچ تغییر مدل، prompt یا موتوری بدون اجرای eval روی دیتاست طلایی و
> **عدم افت** متریک‌ها، به production نمی‌رود.

این همان تعمیمِ «گارد بازگشت» نسخهٔ ۳٫۱ مخزن به سطح کل برنامه است.
