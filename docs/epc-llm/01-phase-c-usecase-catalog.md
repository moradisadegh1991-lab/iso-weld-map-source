## ۱. روش امتیازدهی

هر مورد کاربرد با چهار معیار سنجیده شده است:

| معیار | مقیاس | توضیح |
|---|---|---|
| **ارزش (V)** | ۱–۵ | اثر مستقیم بر هزینه، زمان یا کیفیت |
| **سختی فنی (T)** | ۱–۵ | ۱ = ساده، ۵ = پژوهشی |
| **آمادگی داده (D)** | ۱–۵ | ۵ = داده تمیز و در دسترس، ۱ = باید از صفر جمع شود |
| **ریسک ایمنی/انطباق (R)** | ک/م/ز | اگر خروجی غلط باشد، چقدر خطرناک است |

**امتیاز اولویت** = `V × D ÷ T` — یعنی ارزش بالا با دادهٔ آماده و سختی کم، اول.

**نقش LLM** در هر مورد یکی از این چهار است:
- `EXTRACT` — استخراج دادهٔ ساخت‌یافته از سند/تصویر (کم‌ریسک‌ترین و ارزشمندترین)
- `CLASSIFY` — طبقه‌بندی، خوشه‌بندی، مسیریابی
- `DRAFT` — پیش‌نویس متن برای بازبینی انسان
- `REASON` — استدلال چندمرحله‌ای (پرریسک‌ترین؛ همیشه با موتور قطعی مهار شود)

## ۳. شرح تفصیلی موارد کلیدی

### C-02 · رجیستر جوش و اسپول‌بندی — هستهٔ MVP

**وضعیت فعلی:** موجود در `lib/engine.js`. قواعد پیاده‌شده:
Tie-in = ۱ جوش Field · زانو با pup = ۴ جوش / بدون pup = ۲ · سه‌راهی = ۳ یا ۶ با pup ·
تبدیل = ۲ · فلنج WN = ۱ · شیر BW = ۲ · شیر فلنجی = ۰ ·
ران بلندتر از `maxPipeLength` → girth weld میانی · مرز اسپول روی جوش Field.

**آنچه باید اضافه شود:**
- شناسهٔ پایدار جوش (`weld_uid`) که در رویژن‌های بعدی نقشه **حفظ** شود —
  این کلید اصلی کل مدل دادهٔ برنامه است
- ذخیره در پایگاه داده به‌جای حافظهٔ مرورگر
- نسخه‌بندی: هر رجیستر به `(document_no, revision, sheet, file_hash)` قفل شود

**ریسک ایمنی: زیاد.** خروجی بدون تأیید مهندس پایپینگ نباید به کارگاه برود.
disclaimer فعلی در README باید در UI هم روی هر خروجی چاپ شود.

### C-04 · کنترل رویژن — پرارزش‌ترین قابلیت با کمترین پیچیدگی

**مسئله:** رایج‌ترین ریشهٔ دوباره‌کاری در فاز C، ساخت بر اساس رویژن منسوخ است.

**راه‌حل:**
1. استخراج `(document_no, revision, revision_date)` از title block — LLM اینجا فقط
   ۳ فیلد می‌خواند، دقتش بسیار بالاست
2. مقایسه با آخرین رویژن ثبت‌شده در سامانه
3. اگر رویژن جدیدتر است → اجرای مجدد موتور → **diff رجیستر جوش**:
   کدام جوش اضافه شد، کدام حذف، کدام قطرش عوض شد
4. هشدار خودکار به کارگاه ساخت برای اسپول‌هایی که **قبلاً ساخته شده‌اند** و
   رویژن جدید آن‌ها را تغییر داده — این تنها خروجی‌ای است که مستقیماً
   ریال جلوی ضرر را می‌گیرد

**تخمین ارزش:** هر اسپول دوباره‌کاری‌شده = هزینهٔ متریال + جوشکاری + NDT + تأخیر.

### C-07 · آشتی‌دهی متریال — بیشترین ROI کوتاه‌مدت

زنجیرهٔ کامل که امروز در پنج سامانهٔ جدا (و چند اکسل) زندگی می‌کند:

```
MTO طراحی → MR → RFQ/PO → Expediting → MRR (ورود انبار)
   → انبارش/preservation → MIR (صدور به سایت) → نصب‌شده (از رجیستر جوش)
   → مازاد
```

**نقش LLM:** فقط در استخراج از اسناد نیمه‌ساخت‌یافته (MRR اسکن‌شده، پکینگ‌لیست
تأمین‌کننده، صورت‌جلسهٔ ورود). **تطبیق خودکار قطعی است، نه مدل‌محور** —
با کلید `(tag, size, schedule, material_spec, rating)`.

**خروجی:**
- گزارش مغایرت به تفکیک قلم
- «متریالِ صادرشده ولی نصب‌نشده» → کاندید سرقت، گمشدگی یا کار ناتمام
- «نصب‌شده ولی صادرنشده» → خطای ثبت یا مصرف از قلم دیگر
- پیش‌بینی کسری بر اساس نرخ مصرف و لیدتایم

**چالش واقعی:** یکسان‌سازی نام‌گذاری اقلام بین MTO طراحی و کد کالای انبار.
اینجا یک لایهٔ **نگاشت معنایی (semantic matching)** با embedding لازم است —
و این تنها جایی است که LLM در این ماژول واقعاً ارزش افزوده دارد.

### C-13 · گزارش روزانهٔ فارسی → دادهٔ ساخت‌یافته

**ورودی نمونه (واقع‌گرایانه):**
> «امروز اکیپ جوشکاری آقای رضایی روی خط ۱۸ اینچ واحد ۳ کار کرد، ۴ تا جوش
> سرجوش زده شد ولی بعد از ناهار به‌خاطر نبود الکترود E7018 کار خوابید.
> داربست ردیف B هنوز نصب نشده.»

**خروجی هدف:**
```json
{
  "report_date": "1405-06-30",
  "crew": "welding_rezaei",
  "area": "unit_3",
  "line_no": "18\"-...",
  "activities": [{"type": "butt_weld", "qty": 4, "uom": "joint"}],
  "manhours": {"welder": 6, "fitter": 6},
  "blockers": [
    {"category": "material_shortage", "item": "E7018 electrode", "impact_hours": 3},
    {"category": "scaffolding", "location": "row_B", "status": "not_installed"}
  ]
}
```

**چرا ارزشمند است:** این دادهٔ ساخت‌یافته هم‌زمان سه چیز را تغذیه می‌کند —
S-curve پیشرفت، تحلیل بهره‌وری (unit rate)، و **بانک شواهد ادعای تأخیر (C-20)**.
امروز این اطلاعات در دفترچه و واتس‌اپ گم می‌شود.

**نکتهٔ فنی:** این یک مورد کلاسیک برای **fine-tune سبک (LoRA)** روی یک مدل
open-weight چندزبانه است، چون لحن و اصطلاحات گزارش‌های سایت بسیار محلی است.
قبل از fine-tune، اول با few-shot prompting و دیتاست طلایی baseline بگیرید.

### C-16 · ایجنت RFI/TQ

**جریان:**
```
ایمیل/سامانه → استخراج (شماره، دیسیپلین، خط/تگ، فوریت)
  → جست‌وجوی RAG در: Spec پروژه، Piping Class، نقشهٔ مرتبط، RFIهای مشابه تاریخی
  → پیش‌نویس پاسخ با ارجاع دقیق (سند، بند، صفحه)
  → صف تأیید مهندس دیسیپلین → ارسال
```

**قاعدهٔ سخت:** ایجنت **هرگز** پاسخ را مستقیم ارسال نمی‌کند. متریک موفقیت
«نرخ پذیرش پیش‌نویس بدون ویرایش» است، نه «تعداد RFI بسته‌شده».

**ارزش پنهان:** بانک RFIهای تاریخی با پاسخ، سرمایهٔ دانشی شرکت است که امروز
بلااستفاده در آرشیو خوابیده. همین یک قابلیت، تکرار سؤالات را به‌شدت کم می‌کند.

---

### C-19 · PTW/JSA — تنها موردی که باید محافظه‌کارانه‌ترین رفتار را داشته باشد

ریسک ایمنی **زیاد**. LLM اینجا فقط اجازه دارد:
- بررسی **کامل بودن** فرم (فیلد خالی، امضای غایب، تاریخ منقضی)
- **یادآوری** خطرات مرتبط از بانک حوادث تاریخی مشابه
- **پرچم‌گذاری** تناقض آشکار (مثلاً کار گرم در ناحیه‌ای که همزمان PTW کار در
  فضای بسته با گاز قابل اشتعال فعال دارد)

اجازه **ندارد**: صدور، تأیید، یا رد PTW. این کاملاً دست انسان می‌ماند.
