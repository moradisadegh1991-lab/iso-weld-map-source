# راه‌اندازی فاز ۱ — گام به گام

> در هر لحظه: `npm run doctor` می‌گوید کجاییم و گام بعدی چیست.

این سند ترتیب است. هر گام به گام قبلی وابسته است، و شکستِ پرش از روی یک گام
معمولاً واضح نیست: فهرست پروژهٔ خالی، چکی که همه‌چیز را «قابل بررسی نیست»
گزارش می‌کند، رجیستری که درصد NDT ندارد.

---

## گام ۱ · پایگاه داده

سه مسیر، به ترتیب واقع‌بینی:

| مسیر | چه وقت | چطور |
|---|---|---|
| **PGlite** | همین حالا، روی لپ‌تاپ، بدون هیچ نصبی | کاری نکنید — پیش‌فرض است |
| **Postgres در Docker** | تیم دو نفره، تست روی داده واقعی | `docker run -e POSTGRES_PASSWORD=… -p 5432:5432 postgres:16` |
| **Postgres سازمانی** | تولید | DBA یک دیتابیس و یک کاربر می‌دهد |

```bash
export DATABASE_URL=postgres://isoweld:PASSWORD@host:5432/isoweld
```

**کاربری که اپلیکیشن با آن وصل می‌شود نباید superuser باشد.** PostgreSQL به
superuser اجازهٔ عبور از Row Level Security می‌دهد، و آن‌وقت جداسازی پروژه‌ها
تزئینی است. migration نقش `app_rw` را می‌سازد و کد خودش به آن سقوط می‌کند؛
کاربر اتصال فقط باید حق `SET ROLE app_rw` داشته باشد.

## گام ۲ · Migration

```bash
npm run db:migrate
```

در تولید، این را **گام دیپلوی** کنید و `DB_AUTO_MIGRATE=off` بگذارید — دو
نمونه که همزمان یک migration را اعمال کنند، بدترین جای ممکن برای یادگیری
داستان قفل‌هاست.

migration ویرایش‌شده‌ای که قبلاً اعمال شده رد می‌شود. اگر اسکیما باید عوض
شود، **migration جدید** بنویسید.

## گام ۳ · احراز هویت

```bash
AUTH_MODE=dev            # لپ‌تاپ: توکن همان نام کاربر است
```

برای تولید این کافی نیست و ماژول بدون verifier **throw می‌کند**، نه اینکه به
«اجازه بده» برگردد. Keycloak را که راه انداختید، verifier را در
`lib/server/session.mjs` سیم‌کشی کنید؛ سیاست مجوزدهی که به آن خورانده می‌شود
کامل و تست‌شده است.

## گام ۴ · ارائه‌دهندهٔ مدل

```bash
# امروز
LLM_PROVIDER=anthropic
ANTHROPIC_API_KEY=sk-ant-…

# وقتی خوشه بالا آمد — و این تنها تغییر است
```

بدون این، همه‌چیز جز استخراج کار می‌کند: دکمهٔ «نمونه بدون سرور» کل موتور،
مدل سه‌بعدی و رجیستر را بدون هیچ فراخوانی مدل نشان می‌دهد.

## گام ۵ · ذخیره‌سازی

`STORAGE_ROOT` پیش‌فرض `.storage` است و در اولین آپلود ساخته می‌شود. برای
چندنمونه‌ای، MinIO لازم است (درایورش نوشته شده، به bucket وصل نشده).

## گام ۷ · Piping Class — **مهم‌ترین گامِ داده‌ای**

```
POST /api/piping-classes
PUT  /api/piping-classes/[id]/sizes
```

این یک گام «پیکربندی» نیست؛ **دو چیز را همزمان تعیین می‌کند:**

**یک — چقدر بازرسی.** دستهٔ سرویس، کف کد B31.3 را می‌دهد. `ndt_rules` قواعد
خود پروژه را اضافه می‌کند. قاعده‌ای که **کمتر** از کف کد باشد اعمال می‌شود
(کلاس قرارداد است) ولی به‌عنوان انحراف گزارش می‌شود.

**دو — ضخامت دیواره.** جدول سایز کلاس، **تنها** منبع ضخامت است. تا پرش
نکنید، چک صلاحیت جوشکار ضخامت را `NO_WALL_THICKNESS` گزارش می‌کند — و این
پاس **نیست**.

سایزی که کلاس فهرست نکند، ضخامت ندارد و درون‌یابی نمی‌شود.

## گام ۸ · جوشکارها و صلاحیت‌ها

```
POST /api/welders
POST /api/welders/[id]/qualifications
```

هر گواهی: فرایند، وضعیت آزمون (6G…)، قطر و ضخامت کوپن. از روی همین‌ها بازهٔ
مجاز طبق QW-452.3 و QW-452.1 حساب می‌شود.

**تاریخ انقضا کافی نیست.** طبق QW-322.1 صلاحیت وقتی جوشکار شش ماه از آن
فرایند استفاده نکند ساقط می‌شود — و سامانه این را از خود رکوردهای جوش حساب
می‌کند، نه از کاغذ.

لازم است: **۵۰ ایزومتریک با رجیستر جوش دستیِ تأییدشده**، و برای سنجش لایهٔ
استخراج، **تصویر خود نقشه** کنار هر مورد.

```
eval/cases/golden/SW-265022A.json          ← حقیقت مرجع (داریم)
eval/cases/golden/drawings/SW-265022A.jpg  ← تصویر (نداریم)
```

قالب و راهنمای پر کردن در `eval/cases/golden/_TEMPLATE.json`. این کار مهندس
پایپینگ است، نه کدنویسی — و تا انجام نشود، دقت **موتور** اثبات‌شده می‌ماند
(۲۲/۲۲) ولی دقت **استخراج** اثبات‌نشده.
