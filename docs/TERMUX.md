# اجرای پروژه روی گوشی (Termux)

کل پروژه — سرور، پایگاه داده و رابط کاربری — روی یک گوشی اندروید بالا می‌آید.
مرورگر همان گوشی کلاینت است.

```bash
pkg install -y git
git clone https://github.com/moradisadegh1991-lab/iso-weld-map-source.git
cd iso-weld-map-source
git checkout claude/vigilant-brown-wnaksu   # تا merge نشده
bash tools/termux-setup.sh
npm run dev
```

بعد در مرورگر گوشی: **http://localhost:3000**

اسکریپت idempotent است؛ اگر وسط کار شکست خورد، دوباره اجرایش کنید.

---

## چه چیزی روی گوشی فرق می‌کند

### کامپایلر Next

**این بخش دو بار تصحیح شد — هر دو بار روی گوشی واقعی، نه با حدس.**

اول گفتم Next خودکار به WASM می‌افتد؛ غلط بود — خروجی واقعی شما یک ۴۰۴ روی
دانلود یک باینری android که اصلاً منتشر نشده نشان داد. بعد یک flag
(`experimental.useWasmBinary`) اضافه کردم که مسیر WASM را باز می‌کند — و باز
روی گوشی شکست خورد، این بار بی‌صدا («Failed to load SWC binary»، بدون خط
دانلود). علتش: حتی با آن flag، اولین کاری که Next می‌کند تلاش برای
`require` کردن بستهٔ WASM از `node_modules` است؛ اگر آنجا نباشد، به یک
دانلود دیگر می‌افتد که سرنوشتش به شبکهٔ همان لحظهٔ گوشی بستگی دارد — و آنجا
هم جواب نداد.

راه‌حلی که واقعاً اعتماد می‌شود: **بستهٔ WASM را از قبل نصب کن، هیچ‌وقت به
دانلود لحظه‌ای متکی نباش** — همان اصلی که برای asset های pdf.js هم به کار
رفت. `tools/termux-setup.sh` حالا `@next/swc-wasm-nodejs` را مستقیم و با
همان نسخهٔ Next نصب می‌کند (۵۴ مگابایت، فقط روی گوشی — در `package.json`
نیست تا نصب لپ‌تاپ/سرور/CI را سنگین نکند). بعد از آن، Next این بسته را از
همان پوشهٔ محلی می‌خواند و اصلاً به شبکه دست نمی‌زند.

خود باینری WASM را مستقل از مسیریابی Next سنجیدم — مستقیم `require`ش کردم و
با آن یک قطعه JSX واقعی کامپایل کردم؛ درست کار کرد. چیزی که همچنان نسنجیده
مانده مسیریابی Next روی سخت‌افزار واقعی اندروید است (این‌جا اندرویدی نیست)،
ولی حالا آن مسیریابی هیچ کجا به شبکه یا دانلود وابسته نیست — دقیقاً همان
نقطه‌ای که دو بار قبل شکست خورد.

اولین کامپایل هر صفحه روی گوشی کند است (کامپایلر WASM)؛ بعدی‌ها از کش می‌آیند.

`npm run build` حافظهٔ زیادی می‌خواهد و روی گوشی‌های کم‌رم شکست می‌خورد. برای
کار روی گوشی **حالت `dev` را ترجیح دهید** — چیزی از قابلیت‌ها کم نمی‌شود.

اگر یک روز دوباره «Failed to load SWC binary» دیدید: یک `npm install` سادهٔ
بعدی (بدون `--no-save`) این بستهٔ ۵۴ مگابایتی را چون در `package.json` نیست
پاک می‌کند. `bash tools/termux-setup.sh` را دوباره اجرا کنید — idempotent
است، فقط همان قدم را تکرار می‌کند.

### پایگاه داده

روی لپ‌تاپ پیش‌فرض PGlite است (PostgreSQL کامپایل‌شده به WASM، داخل همان
پروسه). روی گوشی هم اجرا می‌شود، ولی کل دیتابیس را در حافظهٔ پروسه نگه می‌دارد.
Termux خودش PostgreSQL واقعی دارد که سبک‌تر است، و اسکریپت همان را راه می‌اندازد.

اندروید `/run` ندارد، پس سوکت یونیکس در `$PREFIX/tmp` ساخته می‌شود — به همین
دلیل `DATABASE_URL` پارامتر `?host=` دارد.

**بعد از هر ری‌استارت Termux دیتابیس بالا نمی‌آید.** دستی:

```bash
pg_ctl -D $PREFIX/var/lib/postgresql -o "-k $PREFIX/tmp" start
```

### بسته‌های native اختیاری

`@napi-rs/canvas` (وابستهٔ اختیاری pdfjs) و باینری‌های SWC بیلد اندرویدی ندارند.
npm هشدار می‌دهد و رد می‌شود — این خطا نیست. هیچ‌کدام در مسیر اجرای این برنامه
نیستند: رندر PDF در **مرورگر** انجام می‌شود، نه در Node.

### حافظهٔ مرورگر و بوم رندر

نقشهٔ A3 در ۳۰۰ DPI می‌شود ۴۹۵۸×۳۵۰۵ پیکسل، یعنی ۱۷.۴ مگاپیکسل. مرورگرهای
موبایل معمولاً حدود ۱۶.۷ مگاپیکسل (۲^۲۴) سقف دارند — و وقتی رد می‌کنند
**خطا نمی‌دهند**؛ یک بوم خالی تحویل می‌دهند.

برنامه این را فرض نمی‌گیرد: یک پیکسل نشانه در گوشهٔ دور می‌کشد و دوباره
می‌خواندش. اگر زنده نماند، اندازه را کم می‌کند و باز امتحان می‌کند، و **DPI
واقعی** را در نوار وضعیت گزارش می‌دهد — نه آن‌که درخواست شده بود.

پس اگر روی گوشی به‌جای `300 DPI` عدد کمتری دیدید، همان عددی است که واقعاً
رندر شده. تا حدود ۲۵۰ DPI متن BOM هنوز خوانا است.

## کلید API

در `.env.local` که اسکریپت می‌سازد:

```bash
ANTHROPIC_API_KEY=sk-ant-...
```

این فایل gitignore شده است. بدون کلید همه‌چیز جز **استخراج** کار می‌کند؛
دکمهٔ «نمونهٔ بدون سرور» کل موتور و رجیستر را بدون هیچ فراخوانی مدل نشان می‌دهد.

## بررسی سلامت

```bash
npm run doctor
```

گام‌به‌گام می‌گوید کجا ایستاده‌اید و قدم بعدی چیست. روی گوشی گام ۱ باید
`pg` نشان دهد، نه `pglite`.

## آنچه اینجا سنجیده شده و آنچه نشده

**سنجیده‌شده** — همین پیکربندی (PostgreSQL واقعی به‌جای PGlite، با سوکت یونیکس)
روی PostgreSQL 16 اجرا و تأیید شد: هر شش migration، seed، doctor، API پروژه‌ها،
و مهم‌تر از همه **جداسازی RLS** (اتصال به نقش غیرsuperuser ِ `app_rw` می‌افتد و
خواندن بین‌پروژه‌ای صفر برمی‌گرداند). کل مسیر PDF هم با شبیه‌سازی گوشی درایو شد.

**سنجیده‌نشده** — خود Termux. اینجا اندرویدی در دسترس نیست. آنچه از راه دور
سنجیدم: خود باینری WASM (`require`ش کردم و با آن JSX واقعی کامپایل کردم — کار
کرد)، رفتار `useWasmBinary` روی یک پلتفرم پشتیبانی‌شده (no-op تأییدشده)، و
منطق کوچک‌کردن بوم (تست واحد). آنچه نسنجیده مانده مسیریابی Next روی سخت‌افزار
واقعی اندروید است — دقیقاً همان جایی که دو بار قبل شکست خورد. شبیه‌سازی دستگاه
در Playwright فقط viewport و user-agent را عوض می‌کند، نه رفتار واقعی بارگذاری
SWC یا محدودیت تخصیص حافظه را. اولین اجرای واقعی روی گوشی شماست. اگر باز هم
جایی گیر کرد، خروجی کامل ترمینال را بفرستید — نه خلاصه، همان‌طور که دفعهٔ قبل
همان خط ۴۰۴ بود که مشکل واقعی را نشان داد.
