# اجرای پروژه روی گوشی (Termux)

کل پروژه — سرور، پایگاه داده و رابط کاربری — روی یک گوشی اندروید بالا می‌آید.
مرورگر همان گوشی کلاینت است.

```bash
pkg install -y git
git clone https://github.com/moradisadegh1991-lab/iso-weld-map-source.git
cd iso-weld-map-source
git checkout claude/vigilant-brown-wnaksu   # تا merge نشده
bash tools/termux-setup.sh
npm run dev
```

بعد در مرورگر گوشی: **http://localhost:3000**

اسکریپت idempotent است؛ اگر وسط کار شکست خورد، دوباره اجرایش کنید.

## اگر خروجی اسکریپت را نمی‌بینید

بعضی ترمینال‌های اندروید (از جمله wrapper هایی مثل Termux Service Agent)
**فقط stderr را نشان می‌دهند و stdout را می‌بلعند**. نشانه‌اش این است که از یک
دستور پرحرف مثل `npm install` فقط خط‌های `npm notice` را می‌بینید — چون npm
همان‌ها را روی stderr می‌نویسد — و بقیه‌اش انگار اصلاً چاپ نشده.

این اسکریپت با همین فرض نوشته شده: تمام پیام‌هایش روی **stderr** می‌رود،
نشانه‌ها ASCII ساده‌اند (`[ ok ]` / `[ !! ]` / `[FAIL]`)، و یک نسخهٔ کامل هم در
`setup.log` کنار مخزن ذخیره می‌شود. آخرین خط همیشه یک خلاصهٔ تک‌خطی ASCII است:

```
SUMMARY: pg=up wasm=yes key=no log=/.../setup.log
```

اگر حتی همین هم دیده نشد:

```bash
cat setup.log
```

و برای آزمودن اینکه ترمینالتان stdout را نشان می‌دهد یا نه:

```bash
echo stdout-visible; echo stderr-visible >&2
```

اگر فقط دومی را دیدید، فرض بالا برقرار است — و هر دستور تشخیصی دیگری را با
`1>&2` بفرستید تا دیده شود.

> **یک تلهٔ دیگر:** روی اندروید `/tmp` قابل نوشتن نیست. مسیر موقت `$PREFIX/tmp`
> است. `... > /tmp/x.log` بی‌صدا با «Permission denied» شکست می‌خورد.

## چه چیزی روی گوشی فرق می‌کند

### کامپایلر Next

**این بخش دو بار تصحیح شد — هر دو بار روی گوشی واقعی، نه با حدس.**

اول گفتم Next خودکار به WASM می‌افتد؛ غلط بود — خروجی واقعی شما یک ۴۰۴ روی
دانلود یک باینری android که اصلاً منتشر نشده نشان داد. بعد یک flag
(`experimental.useWasmBinary`) اضافه کردم که مسیر WASM را باز می‌کند — و باز
روی گوشی شکست خورد، این بار بی‌صدا («Failed to load SWC binary»، بدون خط
دانلود). علتش: حتی با آن flag، اولین کاری که Next می‌کند تلاش برای
`require` کردن بستهٔ WASM از `node_modules` است؛ اگر آنجا نباشد، به یک
دانلود دیگر می‌افتد که سرنوشتش به شبکهٔ همان لحظهٔ گوشی بستگی دارد — و آنجا
هم جواب نداد.

سومین تلاش هم شکست خورد، و **هر دو فرضم غلط بود**. دو باگ واقعی در Next
14.2.30 زیرش بود:

**۱. flag فقط به یک نقطهٔ فراخوانی می‌رسد.** `experimental.useWasmBinary`
تنها در `build/webpack-config.js` خوانده می‌شود، آن هم فقط موقع ساختن پیکربندی
**کلاینت**. بقیهٔ فراخوانی‌های `loadBindings()` هیچ آرگومانی نمی‌دهند، پس
پیش‌فرض `false` می‌گیرند — و چون نتیجه در یک متغیر ماژول‌سطح (`pendingBindings`)
کش می‌شود، **هر کدام زودتر اجرا شود برنده است**. روی اندروید آن که زودتر اجرا
می‌شد، همانی نبود که flag را حمل می‌کرد.

**۲. بستهٔ نصب‌شده اصلاً دیده نمی‌شود.** Next بسته را این‌طور بار می‌کند:

```js
await import(pathToFileURL(pkgPath).toString())   // pkgPath = "@next/swc-wasm-nodejs"
```

`pathToFileURL` روی یک bare specifier آن را resolve نمی‌کند — تبدیلش می‌کند به
`file:///.../<project>/@next/swc-wasm-nodejs` که هیچ‌وقت وجود ندارد. یعنی آن
۵۴ مگابایتی که در `node_modules` نصب می‌کردم **برای Next نامرئی بود** و همیشه
به دانلود می‌افتاد.

راه‌حل، دو تکه، هر دو سنجیده:

- `tools/swc-wasm-preload.cjs` مقدار `process.versions.webcontainer` را ست
  می‌کند. این تنها شرطی است که در **همهٔ** نقاط فراخوانی مسیر WASM را اجباری
  می‌کند، مستقل از آرگومان. این کلید در کل Next فقط در همان یک خط خوانده
  می‌شود، پس هیچ اثر جانبی دیگری ندارد — و با `process.platform === "android"`
  گارد شده، پس روی لپ‌تاپ/سرور دقیقاً هیچ کاری نمی‌کند.
- اسکریپت بسته را در `node_modules/next/wasm/@next/swc-wasm-nodejs/` می‌گذارد،
  یعنی همان جایی که Next واقعاً می‌خواند. `downloadWasmSwc` اگر آن پوشه موجود
  باشد زودهنگام برمی‌گردد، پس راه‌اندازی **کاملاً آفلاین** می‌شود.

سنجیده شد: با شبیه‌سازی `platform = android`، بدون شبکه، و با فراخوانی
**بدون آرگومانِ** `loadBindings()` — همان نقطه‌ای که شکست می‌خورد — نتیجه
`isWasm = true` شد و هیچ دانلودی هم اتفاق نیفتاد.

**و روی گوشی واقعی هم تأیید شد:**

```
✓ Ready in 2.4s
✓ Compiled / in 12.6s (510 modules)
GET / 200
```

### هشدار کش webpack

روی گوشی این را خواهید دید، و **بی‌خطر است**:

```
<w> [webpack.cache.PackFileCacheStrategy] Caching failed for pack:
    Error: Unable to snapshot resolve dependencies
```

کش فایل‌سیستمی webpack روی فایل‌سیستم اندروید کار نمی‌کند. هزینه‌اش فقط
سرعت است: هر بار که `npm run dev` را از نو اجرا کنید، به‌جای خواندن از کش
دوباره کامپایل می‌کند (حدود ۱۲ ثانیه برای صفحهٔ اول). تا وقتی سرور بالاست،
کامپایل‌های بعدی سریع‌اند (~۱۰۰ms). عمداً دستش نزدم — تنها راه‌حل‌هایش
دستکاری پیکربندی webpack است که نمی‌توانم روی اندروید بسنجم، و خرابی‌ای
هم در کار نیست.

اولین کامپایل هر صفحه روی گوشی کند است (کامپایلر WASM)؛ بعدی‌ها از کش می‌آیند.

`npm run build` حافظهٔ زیادی می‌خواهد و روی گوشی‌های کم‌رم شکست می‌خورد. برای
کار روی گوشی **حالت `dev` را ترجیح دهید** — چیزی از قابلیت‌ها کم نمی‌شود.

اگر یک روز دوباره «Failed to load SWC binary» دیدید: یک `npm install` سادهٔ
بعدی (بدون `--no-save`) این بستهٔ ۵۴ مگابایتی را چون در `package.json` نیست
پاک می‌کند. `bash tools/termux-setup.sh` را دوباره اجرا کنید — idempotent
است، فقط همان قدم را تکرار می‌کند.

### اندازهٔ صفحه

`app/layout.jsx` یک `viewport` export دارد. بدون آن، مرورگر موبایل عرض واقعی
خودش را گزارش نمی‌کند — یک viewport دسکتاپی ۹۸۰ پیکسلی فرض می‌کند و کل صفحه
را کوچک می‌کند تا جا شود. اولین اجرای واقعی روی گوشی دقیقاً همین شکلی بود:
متن از دو طرف بریده و همه‌چیز بزرگ.

بدتر از ظاهرش: `globals.css` از قبل یک چیدمان `@media (max-width:900px)` برای
همین حالت داشت، و با عرض گزارش‌شدهٔ ۹۸۰ **هیچ‌وقت فعال نمی‌شد**. طراحی واکنش‌گرا
تمام مدت آنجا بود و فقط نمی‌توانست اجرا شود.

یک بلوک `max-width:560px` هم اضافه شد برای چیزهایی که در عرض یک گوشی واقعی
هنوز جا نمی‌شدند (دکمه‌های `min-width:210px` که کنار هم صفحه را پهن‌تر از
نمایشگر می‌کردند، و جدول‌ها که حالا داخل قاب خودشان اسکرول می‌شوند).

سنجیده شد روی Pixel 5 (۳۹۳px) و Galaxy S9+ (۳۲۰px): عرض سند دقیقاً برابر
عرض نمایشگر، بدون اسکرول افقی، و هیچ عنصری پهن‌تر از صفحه نیست.

### پایگاه داده

روی لپ‌تاپ پیش‌فرض PGlite است (PostgreSQL کامپایل‌شده به WASM، داخل همان
پروسه). روی گوشی هم اجرا می‌شود، ولی کل دیتابیس را در حافظهٔ پروسه نگه می‌دارد.
Termux خودش PostgreSQL واقعی دارد که سبک‌تر است، و اسکریپت همان را راه می‌اندازد.

اندروید `/run` ندارد، پس سوکت یونیکس در `$PREFIX/tmp` ساخته می‌شود — به همین
دلیل `DATABASE_URL` پارامتر `?host=` دارد.

**بعد از هر ری‌استارت Termux دیتابیس بالا نمی‌آید.** دستی:

```bash
pg_ctl -D $PREFIX/var/lib/postgresql -o "-k $PREFIX/tmp" start
```

### بسته‌های native اختیاری

`@napi-rs/canvas` (وابستهٔ اختیاری pdfjs) و باینری‌های SWC بیلد اندرویدی ندارند.
npm هشدار می‌دهد و رد می‌شود — این خطا نیست. هیچ‌کدام در مسیر اجرای این برنامه
نیستند: رندر PDF در **مرورگر** انجام می‌شود، نه در Node.

### حافظهٔ مرورگر و بوم رندر

نقشهٔ A3 در ۳۰۰ DPI می‌شود ۴۹۵۸×۳۵۰۵ پیکسل، یعنی ۱۷.۴ مگاپیکسل. مرورگرهای
موبایل معمولاً حدود ۱۶.۷ مگاپیکسل (۲^۲۴) سقف دارند — و وقتی رد می‌کنند
**خطا نمی‌دهند**؛ یک بوم خالی تحویل می‌دهند.

برنامه این را فرض نمی‌گیرد: یک پیکسل نشانه در گوشهٔ دور می‌کشد و دوباره
می‌خواندش. اگر زنده نماند، اندازه را کم می‌کند و باز امتحان می‌کند، و **DPI
واقعی** را در نوار وضعیت گزارش می‌دهد — نه آن‌که درخواست شده بود.

پس اگر روی گوشی به‌جای `300 DPI` عدد کمتری دیدید، همان عددی است که واقعاً
رندر شده. تا حدود ۲۵۰ DPI متن BOM هنوز خوانا است.

## آنچه اینجا سنجیده شده و آنچه نشده

**سنجیده‌شده** — همین پیکربندی (PostgreSQL واقعی به‌جای PGlite، با سوکت یونیکس)
روی PostgreSQL 16 اجرا و تأیید شد: هر شش migration، seed، doctor، API پروژه‌ها،
و مهم‌تر از همه **جداسازی RLS** (اتصال به نقش غیرsuperuser ِ `app_rw` می‌افتد و
خواندن بین‌پروژه‌ای صفر برمی‌گرداند). کل مسیر PDF هم با شبیه‌سازی گوشی درایو شد.

**سنجیده‌نشده** — خود Termux. اینجا اندرویدی در دسترس نیست. آنچه از راه دور
سنجیدم: خود باینری WASM (`require`ش کردم و با آن JSX واقعی کامپایل کردم — کار
کرد)، رفتار `useWasmBinary` روی یک پلتفرم پشتیبانی‌شده (no-op تأییدشده)، و
منطق کوچک‌کردن بوم (تست واحد). آنچه نسنجیده مانده مسیریابی Next روی سخت‌افزار
واقعی اندروید است — دقیقاً همان جایی که دو بار قبل شکست خورد. شبیه‌سازی دستگاه
در Playwright فقط viewport و user-agent را عوض می‌کند، نه رفتار واقعی بارگذاری
SWC یا محدودیت تخصیص حافظه را. اولین اجرای واقعی روی گوشی شماست. اگر باز هم
جایی گیر کرد، خروجی کامل ترمینال را بفرستید — نه خلاصه، همان‌طور که دفعهٔ قبل
همان خط ۴۰۴ بود که مشکل واقعی را نشان داد.
