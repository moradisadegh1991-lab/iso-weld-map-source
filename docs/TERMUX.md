# اجرای پروژه روی گوشی (Termux)

کل پروژه — سرور، پایگاه داده و رابط کاربری — روی یک گوشی اندروید بالا می‌آید.
مرورگر همان گوشی کلاینت است.

```bash
pkg install -y git
git clone <repo> && cd iso-weld-map-source
bash tools/termux-setup.sh
npm run dev
```

بعد در مرورگر گوشی: **http://localhost:3000**

اسکریپت idempotent است؛ اگر وسط کار شکست خورد، دوباره اجرایش کنید.

---

## چه چیزی روی گوشی فرق می‌کند

### کامپایلر Next

**تصحیح — اولین نسخهٔ این راهنما اشتباه می‌گفت** که Next روی اندروید خودکار
به WASM می‌افتد. در عمل، در Next 14.2.30 این‌طور نیست: مسیر افتادن به WASM
پشت یک flag تنظیمات قفل است که به‌صورت پیش‌فرض خاموش است. بدونش، Next سعی
می‌کند یک باینری native برای اندروید از npm **دانلود** کند — که چنین بسته‌ای
اصلاً منتشر نشده (۴۰۴) — و آن خطا مدیریت نمی‌شود، پس کل فرایند از کار می‌افتد:

```
Failed to download swc package from .../@next/swc-android-arm64/...
Error: request failed with status 404
```

این را با خواندن `node_modules/next/dist/build/swc/index.js` تأیید کردم:
`aarch64-linux-android` در فهرست «پلتفرم‌هایی که باید اول WASM را امتحان کنند»
هست، ولی آن امتحان به `experimental.useWasmBinary` نیاز دارد که پیش‌فرضش
`false` است.

`next.config.mjs` این flag را روشن می‌کند. روی گوشی، مسیر WASM را از همان اول
امتحان می‌کند و کار می‌کند — کندتر از باینری native، ولی کار می‌کند. روی
لپ‌تاپ/سرور (که باینری native دارد) این flag یک no-op بی‌خطر است: فقط یک
هشدار چاپ می‌شود و کامپایلر native سریع مثل قبل بارگذاری می‌شود — همین‌جا
سنجیدمش.

اولین کامپایل هر صفحه روی گوشی کند است (کامپایلر WASM)؛ بعدی‌ها از کش می‌آیند.

`npm run build` حافظهٔ زیادی می‌خواهد و روی گوشی‌های کم‌رم شکست می‌خورد. برای
کار روی گوشی **حالت `dev` را ترجیح دهید** — چیزی از قابلیت‌ها کم نمی‌شود.

### پایگاه داده

روی لپ‌تاپ پیش‌فرض PGlite است (PostgreSQL کامپایل‌شده به WASM، داخل همان
پروسه). روی گوشی هم اجرا می‌شود، ولی کل دیتابیس را در حافظهٔ پروسه نگه می‌دارد.
Termux خودش PostgreSQL واقعی دارد که سبک‌تر است، و اسکریپت همان را راه می‌اندازد.

اندروید `/run` ندارد، پس سوکت یونیکس در `$PREFIX/tmp` ساخته می‌شود — به همین
دلیل `DATABASE_URL` پارامتر `?host=` دارد.

**بعد از هر ری‌استارت Termux دیتابیس بالا نمی‌آید.** دستی:

```bash
pg_ctl -D $PREFIX/var/lib/postgresql -o "-k $PREFIX/tmp" start
```

### بسته‌های native اختیاری

`@napi-rs/canvas` (وابستهٔ اختیاری pdfjs) و باینری‌های SWC بیلد اندرویدی ندارند.
npm هشدار می‌دهد و رد می‌شود — این خطا نیست. هیچ‌کدام در مسیر اجرای این برنامه
نیستند: رندر PDF در **مرورگر** انجام می‌شود، نه در Node.

### حافظهٔ مرورگر و بوم رندر

نقشهٔ A3 در ۳۰۰ DPI می‌شود ۴۹۵۸×۳۵۰۵ پیکسل، یعنی ۱۷.۴ مگاپیکسل. مرورگرهای
موبایل معمولاً حدود ۱۶.۷ مگاپیکسل (۲^۲۴) سقف دارند — و وقتی رد می‌کنند
**خطا نمی‌دهند**؛ یک بوم خالی تحویل می‌دهند.

برنامه این را فرض نمی‌گیرد: یک پیکسل نشانه در گوشهٔ دور می‌کشد و دوباره
می‌خواندش. اگر زنده نماند، اندازه را کم می‌کند و باز امتحان می‌کند، و **DPI
واقعی** را در نوار وضعیت گزارش می‌دهد — نه آن‌که درخواست شده بود.

پس اگر روی گوشی به‌جای `300 DPI` عدد کمتری دیدید، همان عددی است که واقعاً
رندر شده. تا حدود ۲۵۰ DPI متن BOM هنوز خوانا است.

## کلید API

در `.env.local` که اسکریپت می‌سازد:

```bash
ANTHROPIC_API_KEY=sk-ant-...
```

این فایل gitignore شده است. بدون کلید همه‌چیز جز **استخراج** کار می‌کند؛
دکمهٔ «نمونهٔ بدون سرور» کل موتور و رجیستر را بدون هیچ فراخوانی مدل نشان می‌دهد.

## بررسی سلامت

```bash
npm run doctor
```

گام‌به‌گام می‌گوید کجا ایستاده‌اید و قدم بعدی چیست. روی گوشی گام ۱ باید
`pg` نشان دهد، نه `pglite`.

## آنچه اینجا سنجیده شده و آنچه نشده

**سنجیده‌شده** — همین پیکربندی (PostgreSQL واقعی به‌جای PGlite، با سوکت یونیکس)
روی PostgreSQL 16 اجرا و تأیید شد: هر شش migration، seed، doctor، API پروژه‌ها،
و مهم‌تر از همه **جداسازی RLS** (اتصال به نقش غیرsuperuser ِ `app_rw` می‌افتد و
خواندن بین‌پروژه‌ای صفر برمی‌گرداند). کل مسیر PDF هم با شبیه‌سازی گوشی درایو شد.

**سنجیده‌نشده** — خود Termux. اینجا اندرویدی در دسترس نیست. مسیر
`useWasmBinary` را از روی سورس‌کد Next تأیید کردم (چه چیزی aarch64-linux-android
را به WASM می‌فرستد، چه چیزی روی این ماشین یک no-op بی‌خطر است) و سقف حافظهٔ
بوم با تست واحد پوشش داده شده، ولی هیچ‌کدام را روی سخت‌افزار اندرویدی واقعی
اجرا نکردم — شبیه‌سازی دستگاه در Playwright فقط viewport و user-agent را عوض
می‌کند، نه رفتار واقعی بارگذاری SWC یا محدودیت تخصیص حافظه را. اولین اجرای
واقعی روی گوشی شماست. اگر جایی گیر کرد، خروجی کامل ترمینال را بفرستید.
