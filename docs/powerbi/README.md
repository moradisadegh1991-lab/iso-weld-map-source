# اتصال Power BI (EPIC-8)

> اسکیمای `reporting` · `db/migrations/006_reporting.sql`

## یک نکتهٔ امنیتی که باید قبل از هر چیز بدانید

در PostgreSQL، یک **view معمولی با دسترسی مالکش اجرا می‌شود** — یعنی Row Level
Security در برابر مالک view سنجیده می‌شود نه در برابر کاربری که کوئری می‌زند.

نتیجه: یک view گزارشی معمولی روی این جدول‌ها، **دادهٔ همهٔ پروژه‌ها** را به هر
کسی که بتواند بخواندش می‌دهد. این نشتی است که **هیچ علامتی ندارد** — اعداد فقط
بزرگ‌تر به نظر می‌رسند.

تست مستقیمش این است:

| | خروجی با scope = پروژهٔ A |
|---|---|
| `CREATE VIEW v AS ...` | `a1, b1` ← **نشت** |
| `CREATE VIEW v WITH (security_invoker = true) AS ...` | `a1` |

پس **هر view در اسکیمای `reporting` با `security_invoker = true` تعریف شده** و
یک تست هم این را مستقیم می‌سنجد، نه اینکه به آن اعتماد کند.

## رشتهٔ اتصال

سیاست‌ها روی `app.project_id` کلید می‌خورند، پس اتصال باید آن را حمل کند.
PostgreSQL گزینه‌های startup را در خود رشتهٔ اتصال می‌پذیرد:

```
postgresql://app_report@host:5432/isoweld?options=-c%20app.project_id%3D<PROJECT-UUID>
```

**یک فایل گزارش، یک پروژه** — و محدوده را پایگاه داده اعمال می‌کند، نه فیلتری
که کسی بتواند حذفش کند.

در Power BI Desktop: `Get Data → PostgreSQL` و در قسمت Advanced، همین رشته را
با `options` بگذارید. بدون آن، مدل **خالی** می‌آید — که رفتار درست است، نه باگ.

نقش `app_report` فقط `SELECT` دارد و هیچ‌جا `BYPASSRLS` نیست.

## مدل ستاره

```
                    dim_project
                         │
   dim_unit ── dim_line ─┼─ dim_document
                   │     │
                   │  fact_weld ──── dim_welder
                   │     │  │
              dim_spool ─┘  └──── fact_ndt
                         
              fact_extraction_edit
```

### ابعاد

| view | دانه |
|---|---|
| `dim_project` · `dim_unit` | پروژه و واحد |
| `dim_line` | خط، به‌همراه Piping Class و دستهٔ سرویس |
| `dim_document` | نقشه و رویژن، با `is_current_revision` |
| `dim_welder` | جوشکار، با فرایندها و نزدیک‌ترین انقضا — برای slicer |
| `dim_spool` | اسپول، با `fab_status` |

### فکت‌ها

| view | دانه | چرا این دانه |
|---|---|---|
| `fact_weld` | یک ردیف به ازای هر جوش در **رجیستر حاکم** | معیارها از پیش محاسبه شده‌اند (`is_welded`، `is_examined`، `awaiting_ndt`) — مدل Power BI نباید «جوش زده شده» را با تست رابطه بیان کند |
| `fact_ndt` | یک ردیف به ازای هر رکورد NDT | `is_first_shot` و `is_first_shot_reject` ستون‌اند، نه محاسبهٔ DAX |
| `fact_extraction_edit` | یک ردیف به ازای هر فیلد اصلاح‌شده | فکت **دقت استخراج** |

### «رجیستر حاکم» یعنی چه

یک نقشه ممکن است چند اجرا داشته باشد. آنکه می‌شمارد، اجرای **تأییدشده** است؛
اگر نبود، آخرین اجرایی که موتور ساخته. `reporting.current_run` این را انتخاب
می‌کند و همهٔ فکت‌ها از آن آویزان‌اند — تا **یک پیش‌نویس منسوخ، عدد پیشرفت را
متورم نکند**.

## view های KPI

برای کارت‌های بالای صفحه، از پیش تجمیع‌شده:

| view | مخاطب |
|---|---|
| `kpi_line_progress` | مدیر ساخت — `pct_welded` و `pct_examined` به تفکیک خط |
| `kpi_welder_performance` | سرپرست QC — نرخ تعمیر روی **شات اول** |
| `kpi_spool_status` | برنامه‌ریزی حمل |
| `kpi_handover_gap` | **فهرست** جوش‌های جوش‌خورده و بازرسی‌نشده، با نام جوشکار |
| `kpi_extraction_accuracy` | خودِ برنامه — کدام فیلد مدل مدام غلط می‌خواند |

`kpi_handover_gap` عمداً فهرست است نه عدد: هر ردیفش یک ITR است که اگر کسی
دنبالش نرود، در dossier نخواهد بود. عدد را می‌شود نگاه کرد و رد شد؛ فهرست را
باید کسی تمام کند.

## دامی که یک بار در آن افتادیم

`kpi_welder_performance` اول به **دو** جدول فکت جوین می‌زد (`fact_weld` و
`fact_ndt`) از یک بعد واحد. این یک **fan-out** است: دو رابطهٔ یک‌به‌چند در یک
کوئری، در هم ضرب می‌شوند.

نتیجه ۹ شات به‌جای ۲ بود — KPIای که بی‌صدا چند برابر شده و **هیچ‌کس زیر سؤال
نمی‌بردش، چون فقط به‌صورت یک کارت دیده می‌شود.**

الان هر فکت **قبل از** جوین تجمیع می‌شود. همین اصل در مدل Power BI هم صادق
است: اگر دو جدول فکت را به یک بعد وصل کردید، مراقب دانه باشید.

## کانال دوم: HTTP

```
GET /api/reports/dashboard?projectId=…
```

همان view ها را می‌خواند، پس تعریف «درصد جوش‌خورده» بین داشبورد و گزارش واگرا
نمی‌شود. برای کسی است که نمی‌تواند از جایی که نشسته اتصال پایگاه داده باز کند —
سرپرست سایت با موبایل، جلسهٔ هفتگی پیشرفت، یا یک اسکریپت.

Power BI Report Server که مستقیم به PostgreSQL وصل می‌شود، **کانال اصلی است و
می‌ماند**: سریع‌تر است، زمان‌بندی refresh دارد و از این اپلیکیشن عبور نمی‌کند.
