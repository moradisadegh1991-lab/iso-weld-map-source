# لایهٔ داده (EPIC-1)

> سند مرجع: `docs/epc-llm/02-reference-architecture.md` §۵ و `03-implementation-backlog.md` EPIC-1

```bash
npm run db:migrate     # اعمال migration ها
npm run db:test        # تست لایهٔ داده روی Postgres واقعی
```

## چرا بدون سرور هم Postgres واقعی است

`DATABASE_URL` تنظیم نشده باشد → **PGlite** بالا می‌آید: همان PostgreSQL که به
WebAssembly کامپایل شده و **داخل همین پروسهٔ Node** اجرا می‌شود.

این یک mock یا جایگزین SQLite نیست. همان `db/migrations/*.sql`، همان `jsonb`،
همان سیاست‌های Row Level Security. یعنی کل لایهٔ داده بدون سرور، بدون کانتینر و
بدون credential تست می‌شود — که وقتی پایگاه دادهٔ production آن طرف شبکه‌ای است
که ماشین توسعه‌دهنده به آن نمی‌رسد، تفاوت بین «تست‌شده» و «امیدواریم کار کند» است.

`DATABASE_URL` تنظیم باشد → `node-postgres` روی سرور واقعی. همان کد، همان SQL.

## جداسازی پروژه‌ها — ساختاری، نه قراردادی

معیار پذیرش story 1.5 این بود: «داده‌های دو پروژه هرگز درهم دیده نمی‌شوند.»
این با `WHERE project_id = ?` در لایهٔ اپلیکیشن تأمین **نمی‌شود** — یک
`WHERE` فراموش‌شده کافی است.

پس در پایگاه داده اعمال می‌شود:

```
۱. هر جدول پروژه‌ای  →  ENABLE + FORCE ROW LEVEL SECURITY
۲. سیاست            →  project_id = current_setting('app.project_id')
۳. اپلیکیشن          →  هرگز superuser نیست؛ نقش app_rw
```

**نکتهٔ سوم حیاتی است.** PostgreSQL به superuser و نقش‌های `BYPASSRLS` همیشه
اجازهٔ عبور از RLS می‌دهد — حتی با `FORCE`. اگر اپلیکیشن با superuser وصل شود،
همهٔ سیاست‌ها تزئینی‌اند. `withProject()` هم متغیر را ست می‌کند و هم به
`app_rw` سقوط می‌کند؛ بدون دومی، اولی بی‌اثر است.

نتیجه: کوئری بدون scope، **پایگاه دادهٔ خالی** می‌بیند. حالت شکست «هیچ‌چیز»
است، نه «جوش‌های یک پروژهٔ دیگر».

```js
await withProject(db, projectId, async () => {
  // اینجا RLS فعال است و فقط دادهٔ همین پروژه دیده می‌شود
});
```

جدول‌های `project` و `project_member` عمداً بیرون از این scope هستند: کاربر
**قبل از** انتخاب پروژه به آن‌ها نگاه می‌کند، پس سیاستی که روی پروژهٔ جاری کلید
بخورد انتخاب پروژه را غیرممکن می‌کند. فیلتر آن‌ها بر اساس **کاربر** است، در
`lib/db/repos/projects.mjs`.

## آدرس‌دهی محتوا‌محور

نقشه زیر SHA-256 بایت‌هایش ذخیره می‌شود. سه چیز همزمان به دست می‌آید:

| | |
|---|---|
| آپلود دوبارهٔ یک برگ | هزینه‌ای ندارد و — مهم‌تر — **دوباره استخراج نمی‌شود**. استخراج یعنی فراخوانی مدل و یک ردیف در صف بازبینی، نه فقط CPU |
| «این رجیستر روی کدام فایل تأیید شد؟» | سال‌ها بعد هم جواب دارد |
| تعویض بی‌صدای فایل زیر یک تأیید | ممکن نیست؛ hash عوض می‌شود |

اگر همان شمارهٔ رویژن با بایت‌های متفاوت ثبت شود، خطای `REVISION_CONTENT_CONFLICT`
می‌گیرید. این یک مشکل انضباط رویژن در پروژه است، نه چیزی که باید پنهان شود.

## زنجیرهٔ ممیزی

```
document (doc_no, revision, sheet, file_sha256)
    └── extraction_run (payload, validation_checks, tokens, model)
            ├── spool
            └── weld (weld_uid, weld_no, shop_field, ...)
```

هیچ چیز محاسبه‌شده‌ای بدون اجرایی که آن را ساخته ذخیره نمی‌شود. رجیستر هرگز یک
ادعای معلق نیست: همیشه به اجرایی اشاره می‌کند که ساختش، و آن اجرا به بایت‌های
سندی که خوانده.

`extraction_run.validation_checks` آرایهٔ `checks` خود موتور است، دست‌نخورده —
شرط لازم برای ردیابی دقت در طول زمان و توجیه دوبارهٔ هر رجیستر.

## تأیید

`extraction_run.approved_sha256` هش **آنچه تأیید شده** را نگه می‌دارد. تأییدی که
ثبت نکند چه چیزی را پوشش می‌دهد، تأیید نیست — یک timestamp است. قید
`approval_is_complete` در پایگاه داده اجازه نمی‌دهد ردیفی `approved` شود بدون
امضاکننده، زمان و هش.

سیاست دسترسی در `lib/authz.mjs` است: **فقط `engineer` رجیستر را تأیید می‌کند.**
ابزار پیش‌نویس می‌دهد؛ فرد واجد صلاحیت امضا می‌کند. این تنها مبنایی است که
اجازه می‌دهد خروجی نزدیک کارگاه ساخت شود، و به‌صورت **کد** بیان شده نه به‌صورت
یک جمله در README.

## شناسهٔ پایدار جوش

`lib/db/weld-uid.mjs` — **موقتی**. مالک واقعی این مسئله story 2.1 در EPIC-2 است.

فعلاً از موقعیت فضایی جوش (کوانتیزه به ۵ میلی‌متر) ساخته می‌شود، نه از شمارهٔ
ترتیبی. شمارهٔ ترتیبی با اضافه شدن یک اتصال در بالادست عوض می‌شود و آن‌وقت همهٔ
جوش‌های خط «جدید» به نظر می‌رسند؛ جوشی که جابه‌جا نشده، شناسه‌اش را نگه می‌دارد.

معاوضهٔ این انتخاب، شکست در جهت مقابل است: یک اصلاح کوچک ابعادی که کل مسیر را
بیشتر از کوانتوم جابه‌جا کند، همهٔ جوش‌ها را جدید نشان می‌دهد. حل همزمان هر دو
به گراف مسیر نیاز دارد نه فقط مختصات — دلیل اینکه EPIC-2 برایش story جدا دارد.

## استقرار واقعی

| مؤلفه | وضعیت |
|---|---|
| اسکیما و migration | ✅ آماده — همین SQL روی Postgres واقعی اجرا می‌شود |
| RLS و نقش `app_rw` | ✅ آماده و تست‌شده |
| ذخیره‌سازی محتوا‌محور | ✅ درایور local کار می‌کند · درایور S3/MinIO نوشته شده، به bucket وصل نشده |
| احراز هویت (Keycloak) | ⚠️ **seam** — `createIdentityResolver(verifier)` نوشته و تست شده، ولی verifier واقعی به سرور Keycloak نیاز دارد |
| مجوزدهی (نقش‌ها) | ✅ کامل و تست‌شده — مستقل از احراز هویت |

تفکیک دو ردیف آخر عمدی است: **مجوزدهی** جایی است که قواعد مسئولیت‌دار زندگی
می‌کنند و باید خوانده، بازبینی و تست شود. **احراز هویت** فقط یک adapter است.
ترتیب درست هم همین است — اول قاعده، بعد سیم‌کشی.
